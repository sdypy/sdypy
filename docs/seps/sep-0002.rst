===============================
SEP 2 — Nomenclature guidelines
===============================

:Authors: Klemen Zaletelj <klemen.zaletelj@fs.uni-lj.si>, Janko Slavič <janko.slavic@fs.uni-lj.si>
:Status: Draft
:Type: Process
:Created: 2021-03-15


Abstract
--------

This SEP gives the nomenclature guidelines for SDyPy. Consistent names let the
packages and modules work together.

Motivation
----------

Different packages often use different names for the same quantity. This makes
the packages difficult to use together.

Detailed description
--------------------

SDyPy nomenclature follows the Python guidelines, given in 
`PEP 8 <https://www.python.org/dev/peps/pep-0008/>`_.

General guidelines
^^^^^^^^^^^^^^^^^^

* `PEP 8 <https://www.python.org/dev/peps/pep-0008/>`_ states that code is read
  much more often than it is written. The names of the variables are therefore
  as descriptive as possible.
  Examples:

  .. code:: python
  
     a = 4 # Not good

     rectangle_height = 4 # Good

  Most code editors have autocomplete. Long variable names therefore do not make
  the code difficult to write.

* If a variable name contains more than one word, the term with a broader meaning
  comes first. The more specific term comes next. This makes the code easier
  to read, because the reader immediately sees the purpose of the variable. Examples:

  .. code:: python

     freq_upper
     freq_lower
     damping_viscous
     damping_hysteretic

  The user determines which term is broader.
  This guideline is a **heuristic for new names, not a rule that overrides the
  canonical table below**. Where the table has an entry for a quantity, that entry
  is normative. A name that conforms to the table is never a word-order violation.
  For example, ``natural_freq`` and ``frf_form`` place the broader term second and
  are canonical nonetheless. The heuristic applies only to a new compound name for
  a quantity that the table does not cover. It yields to an established term of
  art: ``mass_matrix``, not ``matrix_mass``. A name settled that way is then added
  to the table, so the decision is recorded and not argued again.

Common variables in structural dynamics
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The variables that are widely used in structural dynamics are an exception to the
general guidelines above. The conventions below prevent different names for the
same quantity, for example sampling_frequency and freq_sampling. These conventions
are normative.

not record. Where a canonical name replaces no evidenced divergent spelling, the cell

Two entries need a word of explanation.

``EI`` is a scalar bending rigidity, the product of Young's modulus and the
second moment of area. It is not a stiffness matrix. ``stiffness_matrix`` is
therefore the wrong name for it, and this table records no canonical spelling for
it. ``EI`` remains a violation of the snake_case rule for public parameters. The
package that exposes it replaces it with a descriptive snake_case name of the
maintainer's choosing.

``xi`` is canonical for an element natural coordinate and divergent for a
damping ratio. Its meaning therefore depends on the context. A name that exposes
a damping ratio uses ``damping_ratio`` wherever it appears. A finite-element
routine keeps ``xi``, ``eta`` and ``zeta``. Only the unambiguous damping
spellings (``nat_xi``, ``pole_xi``) are in the **Instead of** column. A bare
``xi`` cannot be classified without knowledge of what the routine computes.

Relation to ISO 7626
^^^^^^^^^^^^^^^^^^^^

For the quantities it defines, SDyPy nomenclature follows `ISO 7626`_,
*Mechanical vibration and shock — Experimental determination of mechanical
mobility* [2]_ [3]_ [4]_. The FRF forms agree with the standard: ``'mobility'``
and ``'accelerance'`` are the ISO-preferred terms, and ISO prefers *accelerance*
over the synonym *inertance*.

There is one deliberate divergence. For the ratio of displacement to force ISO
prefers *dynamic compliance*, and SDyPy uses ``'receptance'``. ISO recognises
*receptance* as a synonym; SDyPy keeps it because it is the entrenched term in
the modal-testing literature and the existing API string in ``sdypy-EMA`` and
the pyFRF backend. The audit behind this decision is recorded in `issue #2`_.

A divergence from the ISO-preferred term is permitted, but it is recorded in
this section by the same amendment that adopts the name. An undocumented
divergence is a defect in this SEP, not in the package that follows the table.

Proposing a new term
^^^^^^^^^^^^^^^^^^^^

A name coined for a quantity the canonical table does not cover satisfies both
the general guidelines above and the ISO 7626 terminology, where ISO defines
that quantity. Where ISO defines no term for it, the general guidelines and the
precedence rule govern alone, and the absence of an ISO term is not a violation.

The author of the pull request that introduces the name declares it there, and
the reviewer assesses it. Conformance to this SEP is the author's
responsibility: no tool detects an undeclared new name. The discussion happens
in that pull request, and a separate amendment to this SEP is not required
before it can merge.

Declared names are collected and added to the canonical table by a later
amendment. Recording never gates a feature.

A name is escalated only when the pull request cannot settle it — the guidelines
and ISO conflict, ISO is silent where a term was expected, or the reviewers
disagree. Escalation is an issue on ``sdypy`` followed by a pull request
amending this SEP, and it blocks the contested name alone.

The operational detail — how to run the conformance checker, what it does and
does not decide, and the ordered steps for adding a row to the canonical table —
is in the `nomenclature page`_ of the developer documentation, not here.

Naming of public objects
^^^^^^^^^^^^^^^^^^^^^^^^

The guidelines above cover variables. For all other public names in SDyPy
first-level packages the following conventions apply (PEP 8, made explicit):

* **Modules and packages**: ``snake_case`` words. Established acronym
  sub-package names fixed by SEP 3 / SEP 4 (``EMA``, ``FRF``, ``OMA``) stay
  uppercase.
* **Classes**: ``CapWords``. Acronyms keep their uppercase form inside
  ``CapWords`` names (``FRF``, not ``Frf``).
* **Functions, methods and parameters**: ``snake_case``. Acronyms are written
  in lowercase inside ``snake_case`` names (``add_frf``, ``frf_form``).
  Exception: established criterion functions can be the bare uppercase
  acronym (``MAC``, ``MSF``, ``MCF``). Those three functions also keep the
  modal-literature symbols ``phi_X`` (experimental mode shape), ``phi_A``
  (analytical mode shape) and ``phi`` as their arguments. This exception covers
  those three names only: ``phi`` as a parameter of any other public function is a
  violation of the canonical ``mode_shape``.
* **Counts**: a public name that denotes a number of items is spelled ``n_<plural>``
  (``n_modes``, ``n_nodes``, ``n_elements``, ``n_frames``). A bare ``n`` is not a
  count in a public signature.
* **Indices**: a public name that denotes an index into a collection is spelled
  ``<name>_idx`` (``node_idx``, ``elem_idx``). The ``_ind`` suffix is not used.
* **Constants**: ``ALL_CAPS``.
* **Framework exemption**: names mandated by an external framework keep that
  framework's casing (for example, the Qt ``closeEvent`` override).

Public API surface
^^^^^^^^^^^^^^^^^^

Every first-level package declares its public API with an explicit
``__all__`` in its ``sdypy/<name>/__init__.py``. Only the names curated in
``__all__`` are supported API. Any other module attribute is an
implementation detail. Packages that wrap a backend re-export the curated
names explicitly. They do not star-import the backend, so third-party and
standard-library names never enter the public surface.

Deprecation policy
^^^^^^^^^^^^^^^^^^

When a public name is renamed to conform to these guidelines, the old name is
kept as an alias. The alias emits ``DeprecationWarning`` for all of v1.x. Do not
remove a deprecated alias before v2.0. New code uses the canonical names only.
